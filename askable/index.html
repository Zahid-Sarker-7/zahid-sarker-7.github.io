Case study 02 · Production-style RAG

Askable

Upload a document and ask it questions. Answers are grounded only in that document, streamed word by word, and cited. When the answer isn't there, it says "I couldn't find that" instead of guessing.

RoleSolo: design, build, evaluate
TimelineJun – Oct 2026
StackFastAPI · Elasticsearch · Redis · Next.js
EvalRAGAS harness

01 · ProblemAnswers you can check, from documents you own

"Chat with your docs" is easy to demo and hard to trust. A plain LLM answers from memory. Plain vector search misses exact terms like "SOC 2" or an error code. And an app with uploads has to guarantee that one user can never retrieve another user's document.

Askable is an end-to-end reference for doing it properly: hybrid retrieval, reranking, context compression, per-session isolation, a semantic cache, and token streaming. Retrieval quality is measured, not eyeballed.

02 · ArchitectureRetrieve first, then answer only from that

03 · Key decisionsWhat I chose, and what I gave up

DecisionChoseOverWhy
RetrievalBM25 + kNN, fused with RRFVector search aloneBM25 catches exact terms ("SOC 2", "API key"); vectors catch paraphrase ("get my money back" ≈ "refund"). RRF merges the rankings without tuning score scales.
RankingCross-encoder rerank, keep 5Trusting the fused orderA precise second pass over a small candidate set, before anything reaches the LLM.
ChunkingSemantic chunks + parent documentsFixed-size chunksSplits where the meaning shifts, so a chunk stays on one topic. Small chunks to search, large ones to answer.
IsolationAn owner filter on every searchAn index per userOne field is the whole security boundary: simple to reason about and to test.
CacheSemantic cache, public queries onlyCaching everythingRepeat questions are instant, and private uploads can never leak through the cache.
Output checkFaithfulness judge after the streamChecking before the first tokenNever delays tokens. A low score sends a warning event to the UI.
BackendsMemory · Elasticsearch · Upstash behind one seamOne vendorZero-infra local dev, a full Elasticsearch + Redis stack, and a torch-free serverless profile, all switched by one env var.

04 · Hard problemsWhere it pushed back

Problem 01The eval harness wouldn't finish
Symptom
Eval runs failing part-way through
Actually
The Groq model the app used had been retired, and the free tier rate-limited the judge's many calls.
Fix
Moved to a current model, throttled the runs, and used a smaller judge model with a higher rate limit. Answer relevancy still came back empty (rate-limited), so it's reported as missing rather than estimated.
Problem 02A guardrail that failed silently
Looked like
Every answer passing the faithfulness check
Actually
While preparing this page, the logs showed the judge's model had also been retired. The check was built to fail open, so that a judge outage never blocks answers, and that same design hid a permanent failure.
Fix
The judge now runs on a live model, and a failed or unparsable check returns "unknown" instead of "faithful", so the UI says "couldn't verify". Two regression tests pin it: unparsable output and judge errors can never score as faithful.
Problem 03Reading precision 0.52 honestly
Easy misread
Retrieval is missing the right passages
Actually
Recall is 1.0, so the right passages are retrieved. They share the context with less relevant ones, which is what precision measures.
Caveat
A 5-question set is a smoke test, not a benchmark. It catches regressions; it can't support claims about tuning.
